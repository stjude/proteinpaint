General:
- the GDC dataset (ppgdc) must be deployed together with this server release: the DE counts module in ppgdc depends on four new server helpers injected through refs.dsHelpers (run_python, cacheOrRecompute, cacheFilePath, generateHash), so a newer ppgdc image on an older server would come up unable to build its counts matrix. In the other direction an older ppgdc image is harmless — it simply does not declare rnaseqGeneCount, and the differential expression UI does not appear
- GDC differential expression is gated behind serverconfig.features.gdcDE and is off unless that flag is set, so this release changes nothing for GDC until an instance opts in. When it is on, three further flags tune it: gdcDEmaxCases (default 1500, bounded by matrix memory), gdcDEconcurrency (default 60 concurrent bulk requests, up from an effective 20) and gdcDEbulkChunk (default 3 files per bulk request, set to 1 to disable bulk fetching). The concurrency default triples request load on the GDC API relative to the previous per-file download path and can be dialed back per instance

Features:
- Differential expression now works for datasets that have no static counts HDF5. ds.queries.rnaseqGeneCount may supply buildCountsFile(samples, q) instead of .file, and termdb/DE calls it after the sample groups are resolved — the matrix is built for exactly the samples being compared, and only after the group validation that would otherwise reject the request. Samples whose counts could not be fetched are dropped from both group name arrays, since edge_newh5.R fails hard on a requested sample missing from the HDF5. This is what lets the GDC dataset assemble a raw-counts matrix on demand from its open-access STAR-Counts files; ds.queries.geneExpression cannot be used for DE because it serves uqFPKM, already normalized, while edgeR and the rust wilcoxon pipeline both need raw counts
- ds.queries.rnaseqGeneCount may declare defaultMethod to preselect a DE method in the client's method radio. It only reorders the options, so every method stays selectable and the small-cohort branch (which does not offer wilcoxon below 8 samples per group) is untouched. Datasets that do not declare one are unchanged on the wire: termdbConfig.queries.rnaseqGeneCount stays `true` and only becomes an object when a preference exists. GDC sets wilcoxon, which takes a 1370-case cohort from 119.5s to 4.7s — edgeR's cost grows super-linearly on lopsided groups because filterByExpr keys its CPM cutoff off the smaller group, so at 1356 vs 14 roughly twice as many genes reach estimateDisp
- Cut the cold build of an on-demand counts matrix roughly in half, measured over 300 cases: 16.6s of download and parse with per-file GETs at concurrency 20, versus 8.3s with bulk fetching at concurrency 60. Two changes that only work together — GDC serves single files uncompressed but POST /data with two or more ids returns a gzipped tarball at about 4x fewer bytes, and that compression is what moved the bottleneck off the wire so concurrency could scale again. Raising concurrency alone used to make throughput worse (55 to 47 MB/s from 20 to 80 connections). A third of the gain is a rewritten STAR-Counts parser: only two of the nine columns are needed, so it scans for the tabs it wants rather than splitting every line into nine strings, 28.8ms to 9.3ms per file with output verified identical
- New gdcCounts subdir in cacheJobPolicies, holding per-case counts vectors keyed on the file id and a digest of the gene axis they are aligned to, so a data release that changes the gene model misses rather than serving a vector aligned to the wrong axis. Unlike the existing analysis subdirs these are many small fetches rather than a few heavy computes, so maxPending is set above the download concurrency and the real throttle is mapConcurrent; eviction is registered automatically by CacheManager as for any other entry

Fixes:
- Reading the counts matrix in the rust DEanalysis pipeline was doing one strided HDF5 read per sample. The matrix is stored genes-by-samples and contiguous, so each per-sample slice scattered roughly 59k tiny reads across the dataset — 28.8s of system time on a 1370-sample cohort, against 0.03s to read the same matrix whole. Combined with an O(n^2) sample lookup that allocated two Strings per comparison, and a build-then-transpose that copied the whole matrix a second time in f64, this made the engine 33.4s where the statistics themselves account for about 3s. It now does one bulk read, a HashMap lookup and builds the output directly in the orientation the caller wants: 33.4s to 3.0s with bit-identical output, and CPU utilization rising from 114% to 258% because the work was I/O-blocked and its own threading never engaged
- /termdb?getsamplecount=1 dispatched straight into the sqlite implementation and threw "Cannot read properties of undefined (reading 'tableColumns')" for any dataset without ds.cohort.db, leaving group sample counts stuck on "Loading..." for GDC and MMRF. It now branches on ds.cohort.termdb.filterSamples the same way getSampleList already did, and reports the count using the dataset's own uiLabels vocabulary
- buildGroupValues discarded every sample supplied by a dataset without a sqlite termdb. Those datasets key samples by uuid string, which getSampleList already returns for them, but the Number.isInteger guard skipped them all — so a two-group comparison resolved to zero samples on both sides. A string sample id is now taken as the sample name itself. Sqlite datasets are unaffected: a string still has to survive the allSampleSet membership check, and non-integer numbers are still skipped. Diff-methylation shares this resolver and gains the same capability
- The mass groups tab did not pass filter0 when resolving group membership or counts, so datasets that scope every query by a portal cohort filter enumerated the entire dataset instead of the active cohort. On a GDC breast cohort a group filter returned 25,759 cases in 37.9s where the correct answer was 2,802 in 4.8s — both wrong numbers on screen and a needless full-dataset scan on every group edit
- Sample counts in the groups table, the custom-variable menu and the differential expression pre-analysis panel were hardcoded to say "samples" where a dataset's uiLabels calls them cases, and the pre-analysis panel had no header in the groups-menu path — only the DEinput path had one. Its counts are a subset of the group sizes, covering only samples that actually have expression data, so without the header a GDC group of 1570 cases showing as 626 read as a bug. The header now lives in renderPreAnalysisData so both entry points get it
- Restore the #SAMPLE column in the differential expression group builder, disabled behind a TODO pending sample counts for non-sqlite datasets. It is filled asynchronously so one slow count does not hold up the table
- A dataset-level failure while assembling an on-demand counts matrix was absorbed by the per-case skip path, which is meant for the occasional unavailable file: a cache directory problem silently produced a one-column matrix from a 36-case request and wrote a perfectly valid HDF5 that the engines would have analyzed. The run now fails once more than 10% of cases cannot be loaded, and reports the underlying errors rather than only the sample ids. A full cache compute pool is likewise treated as a reason to fail the run rather than to drop cases, since dropping them quietly changes which samples the comparison ran on
- edge_newh5.R reported per-step timings that did not sum to the wall time, because estimateDisp — the dominant cost, 39.7s of a 64s run at 1370 samples — was the one major step without a timer. Instrumentation only; results are unchanged
